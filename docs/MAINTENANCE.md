# 常规维护流程

适用于 GKI 基线更新、回移清理和外部组件更新。先阅读 [项目约束](PROJECT_RULES.md)、[构建说明](BUILDING.md) 和 [贡献说明](CONTRIBUTING.md)。主仓、[固定依赖仓](https://github.com/LunaKernel/ci-dependencies)及 [extra-modules](https://github.com/LunaKernel/extra-modules)分别维护消费、制作和模块模板。

完整流程为：固定本轮目标 → 更新基线与清理回移 → 更新外部组件 → 制作固定依赖 → 测试 CI 与真机验收 → 正式 CI 与 Telegram 交付。

## 1. 开始与边界

1. 检查相关仓库的工作区、分支和远端提交，保护已有改动，记录上次已验收的提交与产物身份。
2. 核对本轮提交、推送、依赖发布和 CI 重试的授权范围；范围内的既有授权继续有效。设备操作与真机验收由用户负责。
3. 本地执行源码审查、补丁演练、来源审计、归档制作和轻量检查；内核、模块及配套工具的实际编译全部在 GitHub Actions 完成。
4. 主仓根 `.env` 是已授权维护的公开 pin 配置。其他凭据读取与远端操作遵循既有授权规则。
5. 按逻辑单元提交，使用 Git 历史回退。源码、pin、快照与文档修改应在最终测试前完成。

## 2. 选择最新已发布 GKI

枚举 [官方发布页](https://source.android.com/docs/core/architecture/kernel/gki-android16-6_12-release-builds)中的已发布、未取消条目，核对官方源码和构建记录。机器可读入口从该页当前链接发现并验证响应结构；不可用时使用发布表。

候选须满足 `android16-6.12`、Linux `6.12.x`、KMI generation 6 和 4 KiB，分别核对 `Makefile`、`build.config.constants` 与官方构建记录。

按 Linux 版本号、`rXX` 修订号依次数值降序选取。例如 `6.12.92 r13` 高于 `6.12.81 r41`，同版本内 `r13` 高于 `r11`。

固定标签、完整提交及查询结果，更新 common pin、版本断言、源码和缓存路径、AutoFDO 身份及相关文档；核对工具链要求。本轮验证使用固定引用。

## 3. 审查并清理全部补丁

从实际应用入口和当前清单枚举完整差异，包括：

- `patches/patch.sh` 的 selected、independent、旧式回移及 Kbuild 回移。
- `patches/patch_external.sh` 的 KMI、SUSFS、KernelSU、BBG 接入和复制文件。
- 依赖仓 AK3 上游模板与 Luna 定制，以及配套组件适配。

逐项依据提交关系、patch-id、最终源码语义、后续 revert 和实际启用路径判定：

| 结论 | 操作 |
| --- | --- |
| 完整吸收 | 删除重复补丁及失去用途的 pin、适配、检查分支 |
| 部分吸收 | 重新整理完整逻辑链，验证剩余前置关系和顺序 |
| 被上游新实现替代 | 使用新实现，清理旧补修 |
| 仍然需要 | 保留来源、目标路径和适用依据 |
| 不适用、有错误或已无实际作用 | 删除并记录简短理由 |

以实际应用集合为准，结合最终源码、配置和调用路径判断必要性；应用、撤销或历史祖先关系用于辅助取证。缺少性能实测本身不构成删除理由。

来源和判定写入既有清单，同步数量、版本、路径及实际编译对象。剩余完整集合的应用、幂等、单项撤销和有序重放在第 5 节消费验证中完成。

## 4. 更新外部组件

沿用已采用的官方渠道，在本轮开始时选定最新提交并固定：

| 组件 | 上游渠道 | 联动检查 |
| --- | --- | --- |
| KernelSU | `tiann/KernelSU` 的 `main` | 版本、UAPI、签名、preinit 和官方 Manager |
| SUSFS | `simonpunk/susfs4ksu` 的 `gki-android16-6.12` | common 与 KSU 补丁来自同一提交 |
| Baseband Guard | `vc-teahouse/Baseband-guard` 的 `main` | common 接口、KSU 凭据标记与 LSM 接入 |

优先原样集成，清理上游已吸收的旧适配，核对既有修复是否保留。接口或代理迁移时追踪最终调用链，确认修复实际生效。适配限于必要兼容、已证实的上游问题和明确的项目定制，并记录依据。

长期定制以 [项目约束](PROJECT_RULES.md#2-来源与改动边界) 为准；`OPEN_REDIRECT` 禁用等临时措施每轮复核，上游完整修复后清理重复层。兼容性未解决时继续保留上次已验收版本供使用。

Manager 选用匹配新 KSU 源码、UAPI 和签名要求的官方 CI 产物，固定 run/artifact、摘要与证书，并完成现有验证。AK3 或 extra-modules 有相关更新时，在所属仓库审查并制作固定输入。

## 5. 制作固定依赖与冻结候选

1. 主仓提交新来源 pin、补丁清单和适配，作为固定制作输入。
2. 按 [依赖仓 README](https://github.com/LunaKernel/ci-dependencies#readme) 从该提交的 Linux LF 检出完成官方来源准备、完整审计和制作。仅回移包变化时使用其增量制作入口，复用未变的工具链、AK3 和 OTA 资产。
3. 在干净环境复核包内容、来源与消费者协议，发布新版本并保留旧资产。
4. 主仓回填真实 URL、归档与 manifest 摘要及必要的安装树摘要。从实际发布地址下载，使用正式消费者、完整 `patches/patch.sh` 和 `patches/patch_external.sh` 验证摘要、应用、幂等、撤销、重放及最终源码差异。
5. 完成相关文档与清单修正，执行 `git diff --check` 和 `bash tools/ci/check.sh`（含语法、单元测试与 actionlint）；制作工具变更时执行依赖仓既有轻量检查。通过后提交消费候选并核对工作区。

回移包身份包含 `COMMON_COMMIT`，切换 common 后即使补丁字节未变也要重制。provenance 记录制作输入提交；后续消费 URL/SHA 回填不触发循环打包。仅修改说明文字且未影响包绑定输入时，无需重制资产。

复用固定 `--work` 来源缓存并核验官方身份，临时检出与输出另放目录。使用已提交的 LF 内容，避免 Windows 工作区 CRLF 干扰校验；结束时记录可复用缓存的 Linux 路径及 WSL 发行版。

验证结果绑定提交与输入。已通过的检查仅在相关输入变化或出现新问题时重跑；定向评审优先检查新增差异。

## 6. 测试 CI 与失败处理

在 main 手动派发 `build.yml`，使用默认 `mode=test`，确认跳过整个 Telegram notify job。测试执行完整构建、审计、打包与产物上传，保留真实失败状态和诊断信息；GitHub 通知设置保持现状。

记录精确 run ID、attempt、工作流、事件与完整项目 SHA，持续监控至完成。失败按原因处理：

- 网络或 runner 临时故障：相同输入重试。
- 源码、补丁或依赖问题：修复并提交后重新测试。
- 参考快照 DRIFT：审查保存的差异，更新参考后重新测试。
- 目标 OTA 闭包或关键功能不兼容：修复后再进入发布。

成功后记录 run URL、完整提交、关键阶段耗时、缓存命中、精确 artifact 和原始 Image SHA-256，状态为 `awaiting-device`。冻结该完整候选；后续修改形成新提交时，须以新 SHA 重新测试和验收。

## 7. 真机验收与正式交付

下载精确测试产物，由用户按 [真机验证规则](PROJECT_RULES.md#6-真机验证)完成验收，绑定测试 run/attempt/artifact、完整项目提交、原始 Image SHA-256 和目标 OTA。缺少真实验收结论时，停在成功测试产物与待验信息。

核对用户结论后，在同一 `build.yml` 派发正式构建：

| 输入 | 值 |
| --- | --- |
| `mode` | `release` |
| `validated_run_id` | 已成功且对应用户验收的测试 run ID，正整数 |
| `accepted_image_sha256` | 已验收的原始 Image SHA-256，64 位小写十六进制 |
| `device_acceptance` | 用户确认的简短验收声明，明确设备与 OTA |

详细设备日志留在原有证据位置，公开参数仅填必要声明。验收文档与指导改进在候选冻结前完成，或在交付后单独提交并保留已验收提交引用。

正式 CI 核对测试运行、完整项目提交及固定输入，执行相同完整构建与全部门禁。原始 Image 摘要与验收值一致后，在 `release.tsv` 记录 `accepted` 及验收关联，校验精确 artifact，再发送内核 ZIP 和官方 Manager 到 Telegram。摘要不同则停止交付，查明原因并重新建立测试与验收绑定。归档中的运行时间和目录名不参与 Image 一致性比较。

通知失败时，在 artifact 有效期内仅重试 notify，使用正式 `release.tsv` 已绑定的测试 run/attempt/artifact；测试后来重跑也沿用原绑定。部分发送或响应丢失时先核对交付，避免重复发送。

以测试通过、真机验收通过、正式 CI 成功和 Telegram 交付确认作为流程完成条件。

## 8. 执行与收尾

默认由单一执行者按阶段推进。需要交接或并行时，提供仓库路径、授权范围、固定提交、已完成验证及剩余事项，明确文件和提交归属；同一候选只由一个执行者负责推送、CI 派发与重试。

将可复用反馈合入本指导；具体制作命令归依赖仓 README，补丁结论归既有清单，运行证据归 CI。清理本轮自建且无用途的临时文件，保留来源缓存与验收资料。

结束时核对相关仓库状态，在对话中报告完成阶段、提交、运行及产物链接、验证结果和待验信息。
